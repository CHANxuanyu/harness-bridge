# 产品形态：面向多 coding agent 订阅用户的本地协作工具

_2026-10-06。工作版产品定义；目标用户由用户确认，其余是本轮形成的实现方向，尚非正式发布承诺。_

## 定位

目标用户已经拥有多个 coding agent，例如同时使用 ZCode / GLM、Claude Code 和 Codex。
他们缺少的是：在当前对话里分配工作、调用其他已安装工具、收回可验收的修改，并在换会话后接续任务。

**Harness Bridge 是独立的本地产品，以宿主插件作为主要使用入口。**
插件是用户接触它的方式；独立内核保存任务、管理执行、验证结果。CLI 是稳定接口和高级入口。
首个可用版本不另建聊天界面，用户继续在自己选择的 coding agent 里工作。

产品承诺应是“让你已有的 coding agent 协作”，而不是“多订阅必然更省钱”或“每个工具任意互调”。
每条实际支持的路线都需要明确的能力与验证记录。

## 最终如何使用

1. **一次设置。** 安装本地内核，并在想发起任务的宿主里启用插件。识别本机已有工具、版本和登录方式，
   展示可用路线；需要登录时引导到原工具。安装完成不启动模型调用。
2. **留在当前对话。** 例如在 ZCode 里说：“把这个模块交给 Claude Code 实现，你负责验收；允许一次修复。”
   当前 agent 负责整理范围和验收标准，Bridge 保存任务并在隔离工作区执行。
3. **看到明确进度。** 显示目标项目、执行工具、尝试上限、正在执行／待审查／需要处理的原因。
   用户不写任务 JSON，不搬运提示词，也不打开第二个聊天窗口监督交接。
4. **在原对话验收。** 当前 agent 读取真实 diff 和独立检查结果；需要修改时，在已授权预算内给执行端返修。
   不因会话迁移重新请求同一授权，不因额度或权限问题悄悄切换到另一个付费来源。
5. **把成果交回项目。** 通过验收后提供明确的交付操作：将已审查版本导出或应用到用户选定分支，记录结果。
   “隔离区通过验收”和“项目已收到修改”必须分开显示。冲突需要可恢复的处理流程。
6. **换宿主继续。** 例如离开 ZCode，稍后在 Codex 中说“继续这个项目的 Bridge 任务”。
   新会话读取同一个任务及证据，接手审查；交接的是结构化任务，不是承诺迁移各工具的全部私有聊天上下文。

另一条最终目标路线是 Claude Code 委派给 Codex。它需要新的执行适配器，当前尚未实现。

## 三层形态与职责

```text
日常入口：ZCode 插件 / Codex 插件 / 后续其他宿主入口
                         │
                  同一个本地接口
                         ▼
Bridge 内核：任务与授权范围 · 工作区 · 执行记录 · 独立验证 · 审查 · 交付
                         │
                按能力接入执行适配器
                         ▼
        本机 Claude Code / 后续 Codex、ZCode 等执行端
```

| 部分 | 承担什么 | 边界 |
|---|---|---|
| 宿主插件 | 理解委派意图、整理任务、调用内核、解释进度、审查证据 | 不另存一套权威任务状态；不新增一个隐藏的 supervisor 模型 |
| 本地内核 | 状态、限额、执行生命周期、工作区、验证、交付记录 | 不直接接模型 API；不把宿主退出误当作任务完成 |
| 执行适配器 | 调用已有 coding 工具，解析输出、确认退出、绑定会话 | 每个工具单独验证；共享插件格式不代表共享执行协议 |

### plugin、MCP、独立应用分别处于哪里

- **Plugin 是分发和使用入口。** 同一个内核可以有多个宿主入口，无需指定 Codex 为永久中心。
- **Skill 是入口内的操作流程。** 当前已有 shell 工具，因此 alpha 先通过 Skill 调用 CLI，验证实际使用体验。
- **MCP 是可选的结构化工具接口。** 当宿主无法可靠调用 CLI，或需要稳定的任务查询/操作工具时再加薄封装；
  它复用内核，不成为另一套状态机。MCP 服务进程也不自动等于可脱离宿主运行的任务执行器。
- **独立界面是辅助入口。** 将来可承载配置、全局任务列表、故障处理；目前不为它重建聊天和代码编辑器。

最终安装体验要统一：用户完成一次引导，插件与兼容版本内核能一起更新。当前 alpha 的本地插件目录加源码
环境仍是开发者安装方式，不能宣称已经一键安装、已上官方市场或已支持所有宿主。

## 多订阅用户特别需要的约束

- 区分 **宿主、模型、执行工具、登录/计费来源**。ZCode 中选用的 GLM 与 Claude Code 的本机登录不是同一配置。
  每次委派显示将调用哪个工具；不能为了通过检查改写用户的 provider 配置或删除 nested 标记。
- 利用原工具支持的现有登录方式，不汇集 OAuth 凭据、不出售共享额度、不自动开启额外用量。
  当前 live gate 仍拒绝 API/provider 环境，不能由插件绕过。
- 用户指定执行端；后续可按能力给建议。未取得可靠额度数据时显示“未知”，不做虚假的余额、成本或最优路由。
- 自动换工具还涉及上下文、工作区、预算和模型变化，必须是单独设计的任务操作。
  不把失败任务复制成新任务来重置预算，也不把修复中的同会话恢复伪装成无损跨工具迁移。
- 默认一个任务一个执行者。多任务并行、多 agent 相互辩论不属于第一个可用版本的必要条件。

## 持续运行的真实边界

当前实现是前台 runner。已有任务状态持久化、进程恢复检查；**没有证明关闭宿主后任务一定继续运行**。

最终若要承诺“关掉对话也能做完当前尝试”，需要宿主生命周期以外的本地 worker，以及经过验证的取消和退出确认。
这是后续工程目标，不因本轮加入插件就变成已有能力。

即使有 worker，默认也只完成当前已授权尝试，然后停在待审查状态。新的模型审查/修复仍由活跃宿主负责。
通知可以提醒用户；通知本身不能承诺自动唤醒原来的 AI 对话。宿主不支持回调时，新会话主动查询同一任务。

## 当前路线矩阵

| 路线 / 能力 | 当前证据 | 还缺什么 |
|---|---|---|
| 本地 Codex 会话 → Bridge CLI → Claude Code | T4 初次执行 + 一次受控 repair/resume 真实通过 | 插件加载后的实际委派体验、可靠交付 |
| GLM 操作者 → Bridge CLI → Claude Code | T3 初次执行记录 | 不能据此宣称 ZCode 插件已完整验证 |
| Codex 插件入口 | 本轮包原型，共用 Skill 和 CLI | 宿主启用、路由触发与完整使用验收 |
| ZCode 插件入口 | 本轮包原型，按官方格式提供 manifest 与 marketplace | 本机安装、加载和任务调用验收 |
| Claude Code → Codex | 产品目标 | Codex 执行适配器、调用权限与恢复协议验证 |
| 其他宿主 → ZCode 执行端 | 候选扩展 | 确认实际可用执行接口；本机 PATH 未发现 zcode 命令，不能当作已支持 |
| 跨宿主接管同一任务 | CLI 持久化基础已有 | 共享任务发现、项目绑定与接管操作的产品验收 |
| 验收后正式交回项目 | 尚无专用交付命令 | 导出/应用、冲突、来源与交付版本记录 |

## 从当前原型到可用产品的验收顺序

1. **入口闭环。** Codex 与 ZCode 能发现/安装入口；离线模式完成新入口调用检查，不让用户拼 JSON 或传话。
   安装前后内核版本、状态目录明确；从新会话找到相同任务。再在单独授权下进行入口的真实执行验收。
2. **成果交付。** 对已批准快照导出/应用，源分支变化能检测，冲突不破坏用户修改，交付记录与验收版本一致。
3. **持续运行。** 验证宿主关闭、runner 中断、取消、超时；需要脱离宿主时引入受控 worker。
   “状态保留”和“进程继续运行”分别验收。
4. **第二个执行端。** 优先实现 Codex executor，使至少两套工具能承担执行角色；ZCode 执行端先核实接口。
   全部方向通过能力矩阵逐项开放，不用一个全局“支持”覆盖差异。
5. **可分发版本。** 干净机器安装、兼容升级、卸载保留任务数据、错误诊断、许可证确定。
   用真实项目验证是否减少人工交接；T5 再衡量质量/时间/用量，不提前营销经济收益。

本轮范围：定义产品、提供两个入口的本地包原型、检查包与 CLI 契约；不新增真实模型调用。

## 依据（2026-10-06 核对）

OpenAI 插件支持 Skill、MCP 等组件及本地 marketplace；Skill 可使用宿主已有工具。
这支持先将 CLI 流程封装成插件，但不能证明内核自动安装或后台存活。
[OpenAI 插件打包](https://developers.openai.com/plugins/build/plugins) ·
[OpenAI Skill](https://developers.openai.com/plugins/build/skills)

ZCode 官方文档提供 `.zcode-plugin/plugin.json`、Skill 目录、marketplace 格式及本地安装方式。
据此可以共用工作流并提供宿主 manifest；真实兼容性仍需本机加载验证。
[ZCode 插件文档](https://zcode.z.ai/en/docs/plugin)

上述最终形态和优先级是结合当前实现、用户画像得出的产品判断，非宿主厂商承诺。
