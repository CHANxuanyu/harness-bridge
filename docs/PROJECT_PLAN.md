**版本：2.2 · 日期：2026-10-08 · 作者：Xuanyu CHAN · 状态：W1–W3、W5 已实现；W6 对话视图与视图切换、W7 官方桌面接续、W8 模型/思考强度/权限模式控件与附件、原生提问表单已实现并通过离线/原生窗口检查；W4、W6–W8 的本机真实验收待执行**

本版本由用户的方向调整决定：**RepoBridge 是以项目为中心的轻量本地桌面工作台，让同时拥有多个
coding plan 的用户在一个界面里使用 Codex、Claude Code 等原生 CLI。** 产品摘要见
[PRODUCT_FORM.md](PRODUCT_FORM.md)。`STATUS.md`、`docs/VALIDATION_MATRIX.md` 记录实际完成度；
本文件的拟议能力不表示已有代码，也不新增任何真实模型调用授权。

## 0. 本版替代了什么

v1.5 及以前（下文附录 A）以 “Advisor 会话领导跨 harness Executor 会话” 为 V1 产品定义。以下旧范围
**由本版明确替代**，凡与本版冲突之处以本版为准：

| 旧范围（附录 A） | 本版处理 |

## 1. 产品定义与约束

| 项目 | 定义 |
|---|---|
| 项目（Project） | workspace 的组织中心：一个本地目录（通常是 Git repo 顶层），其会话、交接与文件变更都挂在其下 |
| 会话（Session） | 固定一种 harness 的原生 CLI 会话；绑定项目、实际工作目录、观察到的原生会话 ID 与历次运行 |
| 运行（Run） | 会话的一次进程生命周期：新建或原生恢复；有 pid/进程组、退出码/信号、失败原因 |
| 交接（Handoff） | 从会话 A 到同项目新会话 B 的显式记录与说明；不是同一原生会话的无损切换 |
| 原生 CLI | 负责模型、对话、工具执行、权限判断、原生上下文与历史，使用用户已有登录与计费 |
| App | 本地桌面窗口 + 本地内核：项目/会话登记、PTY 进程托管、旁路事件、单写入约束、交接说明 |

用户约束（逐条来自方向调整）：

1. 项目是 workspace 的组织中心。
2. 每个 session 固定一种 harness。
3. 换 harness 时，在同项目下创建新会话并交接，不伪装成同一个原生 session 的无损切换。
4. 第一版允许用户手动交接，由新 agent 阅读代码和进度继续。
5. 同一实际工作目录默认只有一个由 App 管理的活动写入会话。
6. 用户在 App 内能看见真实对话、执行活动、权限请求、文件变更、失败原因和会话恢复状态。
7. 模型、工具执行和原生上下文仍由各家 CLI 负责。
8. 使用各家允许的原生认证与计费方式，不收集登录令牌，不把用户已有订阅悄悄换成 API 付费。
9. 先做好 Codex 和 Claude Code；现有进程、会话、事件和恢复实现能复用就复用；
   多 agent 规划、自动路由和整合流程不作为首版必经路径；保留已有可用功能和历史证据。

## 2. 技术决定（W0，2026-10-07）

结合已有 Python 内核与本机环境（macOS、Python 3.11/uv、Node 仅用于获取前端库、无 Rust 工具链），
采用以下组合，不再开展多轮选型：

| 层 | 决定 | 理由 |
|---|---|---|
| 内核 | 现有 `harness_bridge` 包内新增 `workbench` 子包，Python 3.11 标准库为主 | 复用进程组/后代观察、环境变量检查、安全 Git 调用、state 目录与测试设施；单一语言 |
| 原生会话 | 终端视图：在 App 自有 PTY 中运行各家 **交互式** CLI（`claude`、`codex`）。对话视图（W6 起）：同一 CLI 的官方结构化协议——Claude Code `-p` stream-json + SDK 控制协议、`codex app-server` | 原生对话、权限判断、登录与计费完全由 CLI 负责；对话视图只渲染原生结构化消息，不解析终端画面；权限答复只来自用户 |
| 窗口 | `pywebview`（macOS 下为 WKWebView）作为可选依赖 `desktop`；未安装时 `--browser` 打开同一界面 | 轻量原生窗口；无需 Electron/Rust；界面在浏览器中也可调试 |
| 前端 | 无构建步骤的 HTML/CSS/JS + 内置 xterm.js 6.0.0 与 fit 插件（MIT，随包分发） | 真实终端渲染；没有 npm 构建链和 CDN 运行时依赖 |
| 本地通信 | 标准库 `ThreadingHTTPServer`，仅监听 127.0.0.1；随机令牌换取 HttpOnly cookie，校验 Host/Origin；SSE 推送、POST 输入 | 不引入 Web 框架；防止其他网页或本机其他来源驱动进程 |
| 旁路事件 | Claude Code：`--settings` 注入只记录的 hooks；Codex：单次 `-c notify` 与 `tui.notifications`（OSC 9） | 均为各家文档化/配置化机制；只记录，不改变决策，不持久修改用户配置 |
| 会话身份 | Claude：`--session-id` 预分配，SessionStart 核对，`--resume` 恢复；Codex：notify 的 thread-id 观测，`codex resume <id>` 恢复 | 能确定的才绑定；未观测显示未知，不按时间/目录猜测 |
| 文件变更 | App 对工作目录执行只读 `git status`/`git diff`（沿用 hooks 关闭等安全参数） | 不依赖 CLI 自述；不修改用户索引和工作区 |
| 状态 | 同一 state 根下独立 `workbench.sqlite3`（项目、会话、运行、事件、交接）及每次运行的输出日志 | 不迁移、不改写旧任务库；旧功能继续可用 |

## 3. 会话、运行与恢复

- **新建**：Claude 以 `claude --session-id <uuid> -n <标题>` 启动；Codex 以 `codex -C <工作目录>` 启动。
  进程 cwd 为会话工作目录，PTY 由 App 创建，进程在新进程组中运行。
- **原生会话 ID**：Claude 预分配 ID，SessionStart hook 观测到的 ID 一致则为“已核对”；用户在 TUI 中
  `/clear`、`/resume` 等导致 ID 变化时，以最新观测为准并记录变化。Codex 在首轮完成的 notify 中
  观测 thread-id；首轮之前为“未知（尚无首轮）”。
- **恢复**：仅对已知原生 ID 提供 “恢复”：Claude `--resume <id>`，Codex `codex resume <id>`。
  原生 CLI 拒绝（例如会话不存在）时显示退出码与输出尾部，不改为新会话。
- **停止**：向进程组发送 SIGHUP（同关闭终端），超时后 SIGTERM/SIGKILL；用已有后代观察确认退出。
  未能确认时显示“退出不明”，并继续占用写入名额。
- **App 退出/崩溃**：会话进程随终端关闭而结束。重启后，状态仍为运行中的运行，若进程（pid + 启动时间）
  已不存在则标为“已中断”，释放写入名额并提供原生恢复；若仍存在则保持占用并提供终止。
- **单写入约束**：在同一 SQLite 事务内检查同一真实工作目录是否已有 starting/running 的运行；
  有则拒绝并说明是哪个会话。首版所有会话均为写入会话；只读会话、worktree 并行留待后续。

## 4. 可见性

| 用户要看到的 | 来源 |
|---|---|
| 真实对话 | 原生 TUI 的终端输出（xterm.js 渲染）；最后输出写入日志，App 重启后仍可查看 |
| 执行活动 | Claude：UserPromptSubmit / PreToolUse / PostToolUse / Stop 等 hooks；Codex：每轮完成 notify；两者均有进程状态 |
| 权限请求 | Claude：Notification(permission_prompt) / PermissionRequest hooks；Codex：OSC 9 approval-requested。由用户在原生终端回答 |
| 文件变更 | 工作目录只读 Git 状态与 diff |
| 失败原因 | 找不到/不可执行的 CLI、被拦截的环境、启动失败、非零退出码/信号（附去控制符的输出尾部）、恢复失败、退出不明 |
| 恢复状态 | 原生 ID 绑定（预分配/已核对/观测/未知）、是否可恢复、最近运行结果、交接链 |

两个 harness 的旁路粒度不同（Codex 的 TUI 不提供逐个工具的外部事件），界面如实显示差异，不补造事件。

## 5. 人工交接

1. 用户在会话 A 选择“交接到另一 harness”。若 A 仍在运行，先停止（同一工作目录只允许一个写入会话）。
2. App 生成交接说明草稿：项目与工作目录、A 的 harness/原生 ID/最后状态、当前分支与 HEAD、
   变更文件与 diffstat、A 中最近的用户请求与执行活动摘要，以及用户填写的“进度与下一步”。
3. 用户编辑并确认。App 在同项目新建会话 B（目标 harness），记录 `handoff_from = A`，保存说明副本。
   用户可选择让 B 启动时把说明作为第一条消息发送（这是一次由用户确认的模型调用），或只启动、自己粘贴。
4. B 阅读代码与说明后继续。A 保留历史，可在不冲突时原生恢复；界面显示 A → B 的交接链。
5. 说明副本存放在 App state 中，不写入用户仓库；不搬运 A 的原生私有上下文。

## 6. 安全、认证与计费

- 会话环境继承用户环境，但移除 `ANTHROPIC_API_KEY`、`OPENAI_API_KEY` 等 API/provider 变量（沿用
  `config.API_PROVIDER_ENV` / `CODEX_PROVIDER_ENV`），只记录和显示变量名。
- App 不读取 `~/.claude`、`~/.codex` 的认证文件，不调用登录接口；未登录时由原生 CLI 自己引导登录。
  对话视图读取 RepoBridge 创建的会话，以及用户在已登记项目范围内发现并明确关联的既有原生会话：
  Claude Code 读取已核对 ID/cwd 的记录文件，Codex 经 app-server 的 `thread/turns/list`。
  发现使用项目范围过滤，不扫描其他项目；接口见 [EXISTING_SESSIONS_API.md](EXISTING_SESSIONS_API.md)。
  Codex 要求刷新登录令牌的请求一律拒绝。
- App 检测到自身运行在另一 agent 会话（`CLAUDECODE`）或云 agent 环境中时，拒绝启动真实会话。
- 从不添加 `--dangerously-skip-permissions`、`--dangerously-bypass-approvals-and-sandbox`、`--bare`，
  不提供 Claude `bypassPermissions` 与 Codex 完全访问。模型、思考强度、权限模式只在用户于 App 中明确选择后，
  用 CLI 自己的请求或参数传入，并以 CLI 的回报为准（W8，DECISIONS 139–142）。`-p` 只用于对话视图的
  stream-json 连接（W6，DECISIONS 132–133）和不建会话的目录探测，且对话连接必须带
  `--permission-prompt-tool stdio`，让权限请求回到用户手中。
- 本地服务只监听 127.0.0.1，令牌 + Host/Origin 校验；不对外提供远程控制。
- 旁路 hooks/notify 只追加本地事件文件，不输出内容、不影响 CLI 决策；内容截断保存。

### 1. 产品定义与已确定的边界

**用户与一个 Advisor 会话合作。Advisor 检查 repo、拆任务、选择 Executor、派发 prompt、接收反馈、
验收和协调整合。Bridge 准备并管理这些子任务的工作区、执行会话、状态和证据。**

| 项目 | 本计划采用的定义 |
|---|---|
| Advisor | 用户选定的现有 agent 会话；有模型、上下文和工具使用能力。代码中的 `supervisor` 对应此角色 |
| Executor | 由 Bridge 为子任务启动并绑定的 agent 会话；使用对应 harness 的模型与工具，在指定工作区执行 |
| Bridge | 确定性本地程序；负责执行机制，不另设规划/审查模型，不直接调用模型 API |
| 用户界面 | 主要是 Advisor 所在的原对话；用户表达目标、允许的工具与预算，并处理必要的选择 |
| Plugin / Skill | 让 Advisor 获得委派、查询、等待、审查、返修、取消与交付的操作能力 |
| 本地 CLI | 内核接口和诊断入口；插件调用它，普通用户不用编写 JSON 或搬运消息 |
| MCP | 后续可选的工具接口封装；只有宿主接入需要时添加，复用同一内核和状态 |

内核角色与厂商分离；本用户的主路径固定为 Astra Advisor + Opus/Flash Executors。
现有 ZCode Advisor 和 Codex Executor 保留，其他方向须单独验证。
同一种 harness 也可承载不同子任务的独立执行会话。支持某宿主作为 Advisor，不等于已支持其作为 Executor。

用户已确认的是上述关系和多订阅用户群。下文的首版范围、默认并发、交付方式与实施顺序，是为使开发可执行
而选定的工作默认；可根据使用反馈修订，不把这些工程选择冒充用户逐项批准。

### 2. 用户最终如何使用

假设用户在 Codex Astra 会话中处理已打开的项目，要求新增 JSON 导出功能：

1. 用户说：“你负责检查 repo 和验收，让 Claude Code Opus 5.5 做复杂的序列化兼容，ZCode GLM 5.3 Flash 做接口明确的命令行接入。
   可以并行，按这个任务预算返修。”当前会话就是 Advisor，无需新开一个主 agent。
2. Advisor 阅读 repo 和适用说明，确认入口、接口、依赖和检查方法，形成总目标及两个子任务。
   它先确定双方共享的导出格式；如果依赖无法预先固定，就改成先后执行。
3. Bridge 为两个子任务准备各自的工作区和执行上下文，启动对应会话。用户看到谁在做什么、
   哪些任务等待依赖、预算是否仍覆盖下一次执行，不需要选择执行目录。
4. Advisor 在原对话中等待/查询结果，读取实际 diff 和独立检查证据。问题回到对应子任务返修。
   另一个子任务不会因为这次返修而被重建或偷偷更换基线。
5. Advisor 选定经过审查的结果，Bridge 在独立整合工作区形成候选版本，运行总目标验收。
   有冲突时明确处理，不能把“两个子任务分别通过”当作“整体功能通过”。
6. 用户得到经过整体验收的本地交付分支，以及变更、检查和剩余问题的摘要。
   应用到当前工作分支、push、PR、merge 依照用户另外给出的范围执行。

单 Executor 时沿用同一流程，只包含一个子任务。用户离开后重新打开会话，可以从项目任务列表接续，
不需要找旧终端、手工复制 prompt，或重新创建同一个任务。

### 3. 会话、子任务和进程不是同一个东西

```text
用户
  ⇅ 对话
Advisor 会话 S（Codex / Astra）
  ⇅ 创建目标、派发、查询、审查、接管、交付
Bridge：总目标 G + 当前 Advisor 绑定 + 持久化事件
  ├─ 难任务 A → 工作区 WA → Claude Code / Opus 5.5 会话 EA
  │                            ├─ 尝试 A1：一个执行进程
  │                            └─ 尝试 A2：新进程，验证后恢复 EA
  └─ 简单任务 B → 工作区 WB → ZCode / GLM 5.3 Flash 会话 EB（P8 离线实现；原生待验收）
                               └─ 尝试 B1：一个执行进程
            ↓ 通过审查的明确版本
         整合工作区 → 总目标验收 → 本地交付分支
```

#### 3.1 Advisor 会话

- 首版使用用户当前已有会话。Bridge 不调用某个模型来创建或维持另一个 Advisor。
- 每个总目标同一时刻只有一个有派发/审查/整合权的 Advisor 绑定。其他会话可查看状态。
- 记录宿主、可获得的原生会话引用，以及 Bridge 生成的绑定 ID 和递增接管代次。
  原生会话 ID 不可用时明确为空；绑定不是对模型身份或操作者权限的强认证。
- 接管在一个事务内替换有效绑定并增加代次。旧会话的迟到派发、审查和整合请求被拒绝。
  已启动的 worker 不因 Advisor 接管被重启；其结果仍回到原子任务。
- Advisor 上下文压缩或新会话接管时，读取目标、约束、子任务、决定、证据和未解决问题。
  传递的是结构化任务上下文，不承诺迁移原宿主的全部私有聊天或内部推理。

#### 3.2 Executor 会话

- 首次委派创建新的执行会话，不附着到用户任意已打开的交互式会话。已有登录可以复用，会话上下文不混用。
- 绑定子任务、harness、仓库身份、工作区和已观察到的原生 session ID；未观察到时记未知。
- 每个子任务同一时刻最多一个执行 attempt。一次修复通常是新进程恢复同一会话，不是新建一个无关子任务。
- 原生恢复能力必须验证。输出 session 不匹配时停止；不默默转成新会话。无法恢复时，先解释限制，
  由 Advisor 在剩余授权内明确选择冷启动继续或结束；沿用原工作和总预算，记录上下文损失。
- 模型/执行端替换和任务范围变更不属于透明恢复。首版不做失败后自动切换订阅或自动委派下一层子 agent。

#### 3.3 Advisor 不在线时

首版正式验收目标：已经启动、已授权的 Executor 尝试可以由受管理的本地 worker 完成，然后保留在待审查状态。
不会自动创建新的 Advisor，也不会自动开始下一次返修或尚未派发的子任务。

通知只负责告知结果可查。宿主是否能唤醒原会话是独立能力，未验证前不承诺。
P3 受管理 worker 已实现，P7 对记录范围内的实际 GUI 生命周期完成验收；简单的 shell `&` 不算通过验收，
也不能把已测 GUI 退出扩大成系统重启或后台服务整体终止保证。

### 4. 首个可用版本的范围

为区分已有代码，将现有实现称为 **V0.1 内核原型**，下一个完整产品验收目标称为 **V1 本地版本**。
这两个名称不自动改变当前 Python 包版本或插件版本。

| 范围 | V1 工作默认 | 暂不纳入 V1 |
|---|---|---|
| 用户与机器 | 单用户、单机，先交付当前 macOS 环境；保留已有 Linux 回归基础 | 团队共享、远程主机执行、Windows 支持承诺 |
| 仓库 | 一个总目标绑定一个已有、干净且有提交的 Git repo | 跨 repo 总目标、自动搬运未提交修改、非 Git 项目 |
| Advisor | 一个现有会话；可记录接管 | Bridge 自己推理的 Advisor、多个 Advisor 同时写同一目标 |
| Executor | 一个或多个子任务；默认同时运行 1 个，可在授权内设置为 2 个 | 首版扩大到任意规模的并发和递归委派 |
| 路线目标 | 主路径为 Codex Astra → Claude Code Opus 5.5 + ZCode GLM 5.3 Flash；现有其他路线保留 | ZCode Executor 在 P8 实现/验收前不宣称可用；不声称任意方向均兼容 |
| 工作区 | 每个活动子任务一个独立 worktree；独立整合工作区 | 多个执行者共同写主目录 |
| 调度 | Advisor 明确启动就绪任务；Bridge 校验依赖、并发和预算 | Bridge 自己规划、闲时启动未派发任务、额度重置后自动续跑 |
| 消息 | 起始任务、结构化进度/结束、审查反馈；按 attempt 边界接续 | 向运行中的任意原生会话实时插话、跨工具共享隐藏思考过程 |
| 交付 | 以最终验收快照生成本地交付分支，明确区分已验收与已交付 | 自动改用户当前分支、自动 push/PR/merge/deploy |
| 界面 | 原会话中的任务摘要；本地 CLI 可诊断 | 独立聊天客户端、完整 IDE、先建大型 dashboard |

V1 必须实测一对二的离线协调，并在单独授权下实测至少一条包含两种执行 harness 的真实路线。
单个 adapter 或插件未通过时可以继续提供标为实验性的子集，但不能把它宣布成完整 V1。

### 5. 从 repo 到可执行工作区

| 环节 | Advisor 的决定 | Bridge 的动作及失败边界 |
|---|---|---|
| 项目绑定 | 使用当前哪个 repo | 规范化绝对路径、识别 Git common dir；多个候选时澄清，不猜路径 |
| 基线 | 起始 ref、依赖结果版本 | 解析为固定 SHA，记录身份；脏源仓库拒绝，不自动 stash/commit |
| 工作区 | 子任务可改范围 | 创建唯一 worktree/分支；重复请求返回同一任务，不复制出第二份工作 |
| 环境准备 | 所需工具及经认可的准备步骤 | 在该工作区运行限定的准备流程，保留结果；失败不启动模型 |
| 上下文 | 任务背景、接口契约、关键文件、验收条件 | 冻结任务包，检查路径和版本；不把整个聊天日志自动发给子 agent |
| 启动 | 哪个执行工具/模型、一次尝试的范围 | 从分配好的 cwd 启动原生 CLI，绑定 attempt 和会话，记录调用证据 |

**目录创建与选择由 Bridge 在启动前完成。** Executor 收到 prompt 时已处于正确的工作区。
当前已有这条路径：`service.py::_prepare_workspace` → adapter 的 cwd → runner 的进程 cwd。

环境准备是独立的执行环节：新 worktree 不自动拥有依赖目录、虚拟环境、密钥或已运行的服务。
V1 由 Advisor 将显式项目配置冻结到 child plan，说明检查命令和准备步骤，不盲目运行新发现的安装脚本，不复制 `.env` 或整个用户配置目录。
准备产生的文件、可复用缓存和外部资源分别记录；共享可写资源/端口存在冲突时，串行或显式分配。
首版不能可靠处理的环境应在模型启动前明确阻塞。

每个宿主通过同一项目登记找到 runtime 和 state 目录。状态留在 repo 和插件缓存之外；安装/更新插件不移动任务。
所有实际操作继续传递明确的 state 路径，验证用目录与日常项目目录分离；不能靠 live-enable 全局目录简化安装。
worktree 是文件/分支隔离，仍共享 Git 元数据，也不是同用户进程间的权限沙箱。

### 6. 派发、回传和 Advisor 操作面

以下是待实现的操作语义，不是当前可复制执行的 CLI 命令。CLI/可选 MCP 必须调用同一 service 层，
不能靠插件说明文字单独承担预算、归属或状态检查。

| 能力 | 输入与主要结果 | 必须守住的条件 |
|---|---|---|
| 绑定项目/创建目标 | repo、目标、约束、总验收、授权范围 → goal 记录 | 已有会话不因绑定而新增推理调用 |
| 绑定/接管 Advisor | goal、会话引用、接管理由 → 有效绑定代次 | 一个活动写入者；旧代次不能变更状态 |
| 创建子任务 | 子任务计划、依赖、执行选择、上下文 → 协调记录；就绪后物化 task/workspace | 归属明确，固定依赖后才冻结执行基线，准备可失败 |
| 派发一次执行 | task、当前 Advisor 绑定、幂等键 → attempt/worker 句柄 | 一任务一 attempt；总预算预留、依赖和并发检查通过才允许 spawn |
| 查询/等待 | goal/task、上次事件游标 → 增量状态和证据索引 | 等待超时不意味着执行失败；查询和重连不启动模型 |
| 审查/返修 | 当前快照、判定和具体反馈 → 状态变化 | 证据绑定；返修作为下一次显式派发计入预算 |
| 暂停派发/取消 | goal 或 task → 停止派发或停止进程的结果 | 暂停不等于挂起进程；取消必须确认受管理执行已退出 |
| 整合/验收/交付 | 获批子任务版本与顺序 → 整合证据、交付分支 | 使用确定快照，整合后再验证，不能越过用户当前工作区 |

#### 6.1 任务包

任务包包含总目标摘要、子任务目标、固定基线、范围、必要文件/接口契约引用、验收条件、限制和返修意见。
文件引用使用仓库内相对路径或显式授权的外部资源，并记录所依据的版本/摘要；参考材料不得隐式变成执行授权。
执行路径、二进制与环境放在独立执行上下文中。无法传递或恢复的上下文明确报告，不能假装继承主会话。

#### 6.2 回传

共同回执包含 goal/task/attempt 身份、状态、序号/时间、原生 session 引用（可未知）、退出确认、
产物/快照引用、独立检查结果、executor 自述、阻塞原因和剩余可观察预算。大日志按需读取，默认给有界摘要。
重放同一事件不重复应用状态；遗漏事件可从持久化游标补读。

不同工具的“进度”能力不同：适配器能解析多少就报告多少，不能把进程还活着描述成实现快完成。
需要澄清但无法在原生运行中安全问答时，结束/阻塞当前尝试，记录问题，下一次带答案继续；不假造通用实时聊天通道。
首版不向正在执行的会话强行注入修改后的任务；需要改要求时先处理当前执行，再建立明确的新版本/新子任务。

### 7. 数据、状态与兼容性

新增协调层围绕现有 task/attempt 建立，优先复用 store、runner、workspace、verifier 和 adapter。
下列字段是完整设计内容；已实现的 P1 契约见 COORDINATION.md / PLANNING.md。TaskSpec 1.0 仍不接收未知字段。

| 实体 | 关键关系与持久化内容 |
|---|---|
| ProjectBinding | 本地 repo 身份、规范路径、runtime/state 位置、环境准备配置版本 |
| Goal | 目标、固定起点、范围、总验收摘要、授权/预算、当前 Advisor 绑定、交付状态 |
| AdvisorBinding | 绑定 ID、宿主/会话引用、代次、接管记录；不是凭据库 |
| ChildTask（协调记录） | goal 归属、子任务计划/依赖、限额；依赖就绪后关联固定 TaskSpec、执行 task ID 与工作区 |
| Attempt / ExecutorBinding | 任务、尝试类型、worker 身份、harness/模型、原生会话、退出与用量证据 |
| Event / Decision | 有序事件、幂等键、Advisor 代次、理由、被审查的精确快照 |
| Integration / Delivery | 输入快照及顺序、整合树、总验收、最终批准、交付分支/commit 与操作回执 |

保留现有子任务状态：CREATED、READY、STARTING、RUNNING、VERIFYING、AWAITING_REVIEW、SUCCEEDED、
FAILED、BLOCKED、INTERRUPTED、CANCELLED。`SUCCEEDED` 仍只表示该子任务候选通过审查。

总目标另设状态：DRAFT → ACTIVE → READY_TO_DELIVER → DELIVERED；需要决策时可标为 NEEDS_ATTENTION，
放弃或终止为 FAILED / CANCELLED。NEEDS_ATTENTION 不自动停止其他独立执行；具体问题在子任务中保留。
暂停派发作为单独控制项，不冒充进程暂停或目标完成。状态转换条件必须在 P1 固定成表并测试。

总目标进入 READY_TO_DELIVER 必须同时满足：全部必需子任务已通过或有用户允许的明确范围修订；所选输入快照有效；
无未解决依赖/冲突或退出不明；整合候选通过总验收并获得当前 Advisor 对精确快照的批准。
交付操作成功且回执验证后才进入 DELIVERED。候选或验收配置发生变化会撤销此前的可交付状态。
不能通过删除失败的必需子任务或降低验收要求来制造成功。

所有派发、预算预留、绑定检查和事件写入在事务中完成。旧的直接 task 操作如果命中新 goal 的子任务，
同样经过协调检查，不能通过换用旧 CLI 绕过总预算或 Advisor 代次。查看和紧急停止不应依赖已失联的 Advisor。
数据库迁移先备份、检查版本、失败可恢复；历史平级任务保持原含义，不编造父目标或补写从未发生的事件。

### 8. 多 Executor 的隔离、依赖与预算

#### 8.1 派发规则

默认最大活动 Executor 数为 1；用户允许并行且配置为 2 时，可启动两个独立子任务。
同一项目的协调 store 对所有 goal 统一限制总并发，避免它们分别绕过该运行实例的限制。
插件对同一个 repo 使用登记的固定 state，不临时另建 state 逃避限额；独立的测试 state 不属于整机统一调度。
没有 slot 时返回明确等待原因，不偷偷排队开跑。
只有 Advisor 已明确派发的尝试可以启动；依赖刚满足或 Advisor 断线都不会触发新的隐式派发。

依赖构成无环图。依赖成果必须是已批准的不可变快照；依赖 A 的 B 在派发前固定其起点，
不能因为 A 后来返修而静默更改 B 的工作区。一个子任务失败时，阻塞其后继；独立任务可按原授权继续。
具体实现采用延迟物化：先保存 B 的协调记录及等待原因，A 的快照批准且可作为固定 Git 基线后，
再创建 B 的执行 TaskSpec 和 worktree。当前 TaskSpec 在 create 时冻结，不能先创建再偷偷改它的 base。
多个依赖先形成已验证的依赖基线，再物化后继；形成不了明确基线时等待 Advisor 处理。
重叠的可修改范围默认不并行；需要竞争方案时必须显式标成互斥候选，只选择一个结果整合。

#### 8.2 预算规则

- 限额分为每次尝试、每个子任务和整个 goal；所有真实执行都计入 goal，包括返修、重试和整合冲突处理。
- 派发前原子预留一次尝试，确认未启动才可释放；spawn 结果未知时保留占用并停止相关重派，避免双花授权。
- 未确认退出的执行同时保留其并发 slot；不能用“连接断了”释放 slot 再启动新进程。
- 并发预留、超时和取消计入方式写入协议；不能把一个失败子任务换 ID 来重置 goal 预算。
- 安装/查询/离线验证不消耗 executor 尝试，但 Advisor 自身的推理由宿主订阅计量，Bridge 无法强制其额度上限。
- turn 限制依赖具体执行工具，必须分开记录参数接受与实际执行约束的证据；不把它当作跨工具等价成本。
- 2026-10-07 用户明确允许按 harness 能力区分预算：新 Codex 任务显式选择内部轮数硬上限不支持，
  使用尝试次数、强制墙钟超时和人工取消；冻结的数字轮数任务不改。订阅来源、权限、工作区与逐次真实授权门禁仍保留。
- 只报告可观察用量。套餐余额、实际账单无法确认时显示未知；不自动开额外用量、充值、切 API provider 或抓取凭据。

已有明确授权覆盖的步骤直接执行；超出工具、次数、范围或时间预算时才需要新的决定。
本计划书本身不授权任何新的真实验证；上轮两次 repair/resume 的授权已用完。

### 9. 执行生命周期与故障处理

V1 需要按尝试启动的受管理本地 worker，使 CLI 可以快速返回句柄，Advisor 可继续查询/审查其他任务。
worker 持有执行进程组、输出解析、超时、取消和验证职责；SQLite 仍是状态权威。
不引入隐藏的模型服务、不依赖常驻网络服务、不因 worker 重启自动再次派发。

macOS 的具体启动/托管机制在 P3 做离线技术验证后固定。是否能脱离宿主、退出后能否确认进程归属，
是发布门槛；未通过就保持前台实验模式，不能把“状态落盘”宣传成“关闭聊天仍继续执行”。

| 情况 | 必须产生的行为 |
|---|---|
| CLI 等待超时或连接丢失 | 可重新查同一个句柄；不把查询超时当模型超时，不重复 spawn |
| Executor 墙钟超时、取消 | 停止其已证明归属的进程组，确认退出后记录结果；不重跑 |
| worker 被杀或崩溃 | 根据持久化阶段恢复；退出不明则 INTERRUPTED，保留证据和预算占用 |
| STARTING 窗口崩溃 | 不声称 exactly-once；无法证明未执行就不自动重派 |
| 权限、认证、额度问题 | 记录可观察原因并阻塞；不自动换账号/provider，不循环等待重置 |
| Advisor 会话结束 | 已启动尝试按约定完成；结果待审查；不自动继续调用主模型或开修复 |
| 新 Advisor 接管 | 增加绑定代次；读取未决任务；不重复创建工作区或启动已有执行 |
| 用户取消整个 goal | 先禁止新派发，再停止活动尝试；有退出不明者就不能声称全部停止 |

手工接管 Executor 的可写目录必须先确认其执行已结束；这与 Advisor 更换会话接管管理权是两种操作。

### 10. 审查、整合和交付

子任务审查复用现有规则：确认退出、固定验收命令、快照完整性、范围检查和实际 diff。
Executor 自述不替代验证。Advisor 的 approve 绑定 task、attempt、版本与快照，候选有变化就重新验证。

整合流程明确为：

1. Advisor 选择已批准的子任务快照和整合顺序。Bridge 保留足以复现的不可变对象，
   不能只记分支名或假定所有修改已被 executor commit。
2. 从总目标固定基线创建 Bridge 自有整合工作区，按记录顺序应用“各自基线 → 已批准树”的完整变更。
   删除、新增、二进制、文件模式等必须覆盖；不得只拷贝工作目录里看见的文件。
3. 有冲突就停在明确的整合问题。需要模型解决时，由 Advisor 创建计入总预算的整合子任务，
   给它最后可用基线和待整合产物，在自己的工作区解决；不改写已批准的原始子任务证据。
4. 在整合候选上运行总目标的独立验收。失败后返修，修改将使此前整合批准失效。
5. Advisor 对整合快照作最终判断。通过后状态为 READY_TO_DELIVER，尚不等于已交付。
6. 按用户指定的本地分支交付方式，生成对应最终快照的 commit/分支，记录精确版本后变为 DELIVERED。
   重试返回同一交付结果；目标分支已存在且不匹配时拒绝覆盖。

V1 默认交付一个新的本地分支，不改当前 checkout。源仓库随后前进时，明确显示交付基线与当前差异；
若用户要求整合最新源版本，需要形成新的候选并重新验收，不能把过期检查沿用到新代码。
正式应用到用户当前分支、发布 PR 或推送是另一个明确动作，不能由子任务 approve 隐式触发。

清理只删除经验证属于 Bridge 且未活动的资源；已交付分支、仍需保留的证据和用户改动不自动删除。
未知退出、未交付结果和保留策略未处理前不清理工作区。

### 11. 安装、宿主接入与能力矩阵

最终安装流程：配置兼容内核 → 在选定的 Advisor 宿主启用插件 → 登记项目与 state →
无推理诊断执行工具及环境 → 展示支持的路线。发现没有登录时引导使用原工具登录，不代取登录令牌。

插件缓存中的文件可独立加载，不假定内核位于缓存旁边。项目登记不依赖某个会话的临时记忆。
版本不兼容先诊断；升级不偷偷启动模型或破坏旧任务；卸载入口默认保留任务数据，数据清理由独立操作完成。

任务记录、原始流和代码产物默认留在本地，不自动上传。Bridge 源码仓库 public 不表示任务数据公开；
发布验证记录只使用脱敏样例和必要摘要，不记录认证值或复制私有聊天内容。

| 入口/执行路线 | 当前事实 | V1 要求 |
|---|---|---|
| Codex 会话 → CLI → Claude Code | 初次执行和一次受控 repair/resume 已真实通过 | 安装后的 Advisor 入口与新协调协议完整验收 |
| GLM 操作者 → CLI → Claude Code | T3 初次执行通过 | 不直接等同于 ZCode 插件路线；需独立验证 |
| Codex 插件 | alpha.2 实际配置安装/启用、原生技能目录加载、默认共享连接通过；当前窗口热刷新未观测 | 原会话完整真实委派、等待、返修、接管与交付 |
| ZCode 插件 | alpha.2 实际安装、技能启用、缓存自检和默认共享连接通过；未触发模型 | Advisor 真实操作流程与宿主生命周期验收 |
| Codex Executor | 离线适配与 stub 闭环已实现，真实派发关闭 | 内部回合上限、订阅/配置证据与原生恢复仍需逐项确认 |
| ZCode Executor | P8.1 无模型能力探针通过；P8.2 离线 adapter 已覆盖模型/目录绑定、原会话返修、取消、预算和独立验收；见 [ZCODE_EXECUTOR.md](ZCODE_EXECUTOR.md) | 真实账号/权限、会话协议、停止和桌面行为待验收；live 仍拒绝 |

每个 adapter 维护能力事实：启动方式、目录指定、流式输出、恢复、取消、限制、认证/计费路径及证据版本。
“安装了 CLI”和“能按订阅安全完成本任务”分开判断。当前 live gate 保持原规则；新方向需要独立设计和验证，
不能通过删掉 provider/nested 标记或放宽权限把未知路线变成可用。

首版不依赖 computer use 驱动执行工具的 UI；执行端没有可靠程序接口时先保持不支持。
本机插件安装确实需要界面时再使用界面操作。产品不能建立在截图轮询和模拟人手输入上。
